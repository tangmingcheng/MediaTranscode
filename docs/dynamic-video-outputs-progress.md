# 视频动态多输出实施记录

## 已确认范围

一路输入，运行中增删多路独立视频转码输出；实时 CLI 与 beta C API 共用生产 DAG。覆盖现有实时视频协议，首项验收为 RTP 输入 → MPEG-TS over RTP 输出，Windows 通过后才进行 RKMPP 同规格验证。首版不增加音频多输出。

删除最后一路后保留输入；持续拥塞或失败只终止问题分支；新增共享编码输出等待正常随机访问点。用户已同意最小必要公开接口扩展及 beta ABI 调整；CLI 使用标准输入命令。不新增调用方推算的容量参数。

## 行业对照与实施前发现

| 行为 | 权威依据 | 当前差距与处理要求 |
|---|---|---|
| 动态连接与删除 | [GStreamer 动态管线](https://gstreamer.freedesktop.org/documentation/application-development/advanced/pipeline-manipulation.html) 的 BLOCK/IDLE、EOS、时钟继承 | 当前图、channel 和 wakeup 注册表无并发变更协议；发布前准备资源，安全点切换并等待在途引用退出，不能直接修改容器。 |
| 多输出隔离 | [GStreamer tee](https://gstreamer.freedesktop.org/documentation/coreelements/tee.html)、[FFmpeg tee/fifo](https://ffmpeg.org/ffmpeg-formats.html#tee) | 当前 atomic fan-out 同时抢所有输出容量，worker 首错停止全图；需分支独立提交及依赖故障域。 |
| 硬件池与所有权 | [FFmpeg AVHWFramesContext](https://ffmpeg.org/doxygen/trunk/structAVHWFramesContext.html)、[AVFrame](https://ffmpeg.org/doxygen/8.0/group__lavu__frame.html) | 某些池固定大小，不能以 initial_pool_size 请求回读证明所有平台的硬上限；现有设备/驱动内存仅可观测。 |

关键事实：`MediaHardwareCapabilityProbe` 的 prepared emission 是临时 codec context 的 readback，context 随局部 RAII 销毁；运行时重新打开 encoder。现有 `MediaPreparedEmissionResolver` 没有生产 `hardwareMemory` envelope，不能宣称新分支设备内存已预留。最终 graph ledger 对所有 encoder 使用单一池产品，异规格输出必须按 producer 核算。

删除截止时间与物理回收必须分开：当前 codec 调用不提供取消参数，视频节点未实现有效 interrupt，worker join 无界。超时不能销毁仍在驱动调用中的对象；退役资源仍需计费。严格有界硬件回收需要具体 adapter 的权威能力证据。

以上为源码和权威资料调查，不能作为动态多输出实现完成或真实验收通过的证据。工作目录已有未跟踪依赖头文件、out 产物及 NUL，本轮不纳入提交、不清理他人产物。
## 本轮集成状态

第十三次 Windows Release 全量构建通过；第 1—8 轮真实流均未通过完整动态验收，逐轮命令、失败与清理结果见 dynamic-video-windows-01.md 至 dynamic-video-windows-08.md。已修复元数据类型、wakeup 所有权、载荷分区与在途引用、终止信用回收、编码器先于帧发布、源代次、prepared 视频源事实及 SDP 用户名语法。第 5—8 轮初始 HEVC 输出持续运行，但新增输出仍未成功；第 7、8 轮暴露 scheduler 及协议输出 builder 的全图单例限制；现已统一按输出 session 校验，并核查动态投影的后续资源和拓扑检查，待第十四次构建及复验。完整编码契约相等的编码组尚未接入生产，不标记功能完成。

硬件准入必须使用运行中的真实 decoder readback。Windows 实际选择 `h264` + CUDA NVDEC：本机 FFmpeg 源码 `libavcodec/nvdec.c` 的 `nvdec_retrieve_data` 在未启用 `AV_HWACCEL_FLAG_UNSAFE_OUTPUT` 时调用 `av_frame_make_writable`；`libavutil/frame.c` 通过独立 CUDA frame allocation 复制并释放只读映射，`libavcodec/decode.c` 在交付调用方前释放内部 `private_ref`。因此可以对已证实 safe-output 的 CUDA 帧按 engine payload 引用硬边界准入；不能只凭 CUDA 名称或 `initial_pool_size` 推断。驱动内部内存仍属于观测范围。

RKMPP 只读能力核查：目标机 FFmpeg 及 `/root/ffmpeg-rockchip` 均为 `d90e3a1c18d7929383cf88c1b3da2e2d1c966cbf`。其 `rkmppdec.c` 对 half 模式设置有限 MPP buffer group，ext 模式使用固定外部池；这与 CUDA 独立输出分配不同，必须形成独立的固定池余量或帧脱离能力证据。尚未进行 RKMPP 本轮真实链路测试，仍严格等待 Windows 先通过。

初始输出与新增输出需要同样的资源隔离：初始 DAG 在启动前按 planner 产品拆共享源与输出账户；动态新增除输出 producer 外，还需覆盖共享 decoder payload 被更多下游引用的保留窗口。退役必须等待真实 worker 退出，初始输出还要等一次性 codec metadata producer 完成，禁止先宣称回收再留下延迟到达的 encoder metadata。

载荷记账需遵循 [FFmpeg AVBuffer](https://ffmpeg.org/doxygen/trunk/group__lavu__buffer.html) 的最终引用释放语义：packet/frame 的数据缓冲与 opaque 元数据生命周期不同，不能把输入压缩包账户随 lineage 一直带到解码后的帧。所有权修复必须同时审查视频解码、滤镜、编码及共享音频解码接缝；源预算还需由真实 decoder 在途事实覆盖下一次原子预留，不能仅清除输出元数据或增加经验倍数。

## 编码组尚待实施项

拓扑统一为共享输入/解码 → 帧分发 → 编码组 → 编码包分发 → 独立协议输出；首路与新增路采用相同段模型。

- planner 在 capability probe 打开新编码器之前匹配已有组的完整合同，源代次、实际设备、转换、尺寸/帧率、RC/GOP、packet layout 及真实 readback 均纳入判定。匹配后只准备协议段；仅新组打开编码器，避免硬件 session 已满时误拒绝可共享输出。
- 组持有编码 segment、编码包分发与租约，输出持有协议 segment 和组引用。runtime segment 使用独立单调 ID。
- 新消费者在自然 RAP 边界加入，复用现有参数集物化；需要证明所选后端的 key 标记及前导帧语义满足独立解码，不能将任意 I 帧等同 IDR。READY 继续以该输出完整 RAP 的最后媒体报文实际提交为准。
- 删除先解除协议订阅并排空；最后消费者实际退役后才解除组的帧订阅、排空并回收编码组。零输出保持输入/解码消费。
- 候选段在事务中拥有，部分启动失败的段留在回收容器；既有组不因候选失败停机。共享 payload 的增量保留预算随真实引用退出回收。

以上尚未接入生产拓扑，也未实测；不计作完成。
