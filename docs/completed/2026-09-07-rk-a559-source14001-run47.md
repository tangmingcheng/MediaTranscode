## 根因与结果

- 启动 API 在目标机 19:39:06.595725 返回 code=0、local_port=15500。
- 19:39:33.114803，输入 pcap 捕获完整 **1402 B** UDP/RTP，源端口15500、目标61884、RTP v2/PT96/SSRC3/sequence1547。IPv4总长1430 B、未分片，捕获载荷同为1402 B。
- 19:39:33.115，RawRtpInputNode 报 `Linux RTP ingress datagram was truncated (native=90)`；接收槽 `maximum_datagram_bytes=1400`，truncations=1、workerErrors=1、errors=1，CLI exit 1。
- 停止 API 19:39:35.215080 返回 code=0。控制脚本 exit130 来自测试收尾 SIGINT，不是先发生的源故障。
- 根因是 `MediaRtpIngressPlan::create` 将有限探测得到的 `observation.maximumDatagramBytes()` 同时用于运行期槽长和容量除数。910个1400 B包均可接收，后续1402 B包超过错误槽长而被截断。这是核心容量规划缺陷；截断拒绝本身正确，不能解析残包。
- 本地有限视频由 FFmpeg 按 pkt_size=1400 发流，未触发此较大包；不能据此前通过证明探测峰值是协议上限。
- 实际硬件链为 h264_rkmpp → scale_rkrga async_depth=0 → hevc_rkmpp、zero_copy=true，VLC 默认 D3D11VA；不足三分钟，完整门禁 **FAIL**。
- CPU平均单核13.030787%、峰值29.629630%；RSS初始27,037,696 B、峰值32,067,584 B。VideoOnly无A/V漂移项。Windows抓包15770 UDP、drop0；本次未用短链路输出证明持续播放或无突发通过。

## 最小修复边界

预探测 transport 已由 `MediaRawRtpBootstrapPlan` 按地址族和原字节预算形成协议接收上限。将该既有事实传回 ingress planner，替代样本峰值用于槽长；样本峰值仍用于验证观测没有超出契约。批次数量继续由原字节预算除以槽长推导，保持硬边界；不新增调用方参数，不按1402调参，不改节点截断保护。

与 [FFmpeg UDP接收覆盖完整数据报范围](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/libavformat/udp.c) 和 [GStreamer udpsrc允许超过预期MTU的数据报](https://gstreamer.freedesktop.org/documentation/udp/udpsrc.html) 的完整接收原则一致。本项目复用既有预分配和planner契约，不引入运行时扩容。IPv4本轮槽长将为既有协议上限65507 B，原4194304 B接收预算可形成64槽、4192448 B池；需要复核批次和乱序容量变化的实际影响。

线程、DAG、所有权和异常传播不变；缺失容量或预算不足在规划阶段失败。Linux/Windows共用该容量规划，Windows截断路径有同类影响；按用户明确要求不做Windows转码实测，不声称全平台运行已验证。
